How It's Built

This site is generated by a small Go program written for it. There is no web framework, no content management system, and no server: the program reads Markdown and typed content, checks it, renders HTML, and writes plain files that are published as a static site. This page walks through how each part works and why it was built that way.

The build pipeline

Every push to the main branch runs the same steps, in this order:

content.go ─┐
templates/ ─┤                       ┌─► HTML pages
notices/   ─┼─► validate ─► render ─┼─► sitemap.xml, robots.txt, security.txt
CHANGELOG  ─┤                       ├─► notices RSS feed
static/    ─┘                       └─► static assets (CSS, JS, images)
                                            │
                                            ▼
                                     static hosting
  1. Validate. Every rule in Validation and safety runs first. Any failure stops the build with a message naming the problem, so nothing broken is ever published.
  2. Load content. Typed content (navigation, roadmap, FAQ, status providers) comes from Go functions in content.go. Notices are read from Markdown files.
  3. Render. Each page is rendered through Go's html/template: a shared layout, shared partials, and one template per page.
  4. Copy and generate. Static assets are copied as-is, and machine-readable files are generated from the same data the pages use.
  5. Publish. The output folder is uploaded to static hosting. A full build takes a few seconds.

Design decisions

DecisionWhy
Static files, no server Nothing to patch, scale, or keep running, and the smallest possible attack surface. A site that only states facts does not need a server.
A purpose-built generator instead of Hugo or a framework The site's rules (approved notice categories, secret scanning, status endpoint checks) are enforced in code, in one place. A general tool would need plugins or conventions to do the same.
Work at build time, not in the browser Search indexes, tables of contents, related links and feeds are computed once per deploy, so pages load fast and work without JavaScript.
Fail the build on bad content A mistake that would be invisible until a visitor found it (a broken link target, a typo in a category, a leaked key) is cheaper to catch before publishing.
JavaScript only where the browser is required Live status must be fetched when the page is viewed, and search is most useful as you type. Everything else is plain HTML.

The generator

One program, three commands

main.go provides three commands that share the same content and templates:

  • build renders the whole site into an output folder. This is what CI runs.
  • serve runs a local web server for development. In this mode templates, notices and static files are read from disk on each request, so an edit shows on refresh without restarting.
  • check runs validation only, without writing anything.

For build, templates, static files and notices are compiled into the program with Go's embed package. The binary that CI runs is self-contained: it cannot pick up a stray file from the working directory by accident.

Content as typed data

Navigation, the roadmap, the FAQ and the list of monitored providers are Go structs returned by functions in content.go. Because they are typed, a missing field or a wrong kind of value is a compile error or a validation error rather than a silently blank page. Adding a roadmap item or FAQ entry is a single edit in one file.

Templates

Pages use Go's html/template, which escapes every value according to where it appears: HTML text, an attribute, a URL, or a script. Content cannot inject markup by mistake. A base layout provides the sidebar, header metadata and footer; shared partials (such as the notice card) are loaded with every page; and each page fills in one content block.

The notices engine

Notices are Markdown files in a notices/ folder. Adding a file is the whole publishing step: the file name becomes the URL, the first heading becomes the title, and the first paragraph becomes the summary. Each file goes through these stages:

  1. Secret scan. The raw file is checked against nine patterns for credentials: cloud access keys, private keys, GitHub, chat-platform and payment-platform tokens, Google API keys, JSON Web Tokens, password = … assignments, and passwords embedded in URLs. A match fails the build and reports the file and line. This happens first because once text is pushed to a public repository it stays in its history even if deleted later.
  2. Front matter. An optional block at the top sets a description, categories, and dates. The parser accepts only those four keys and rejects unknown ones, so a typo fails loudly instead of being ignored.
  3. Categories. Every notice must use at least one approved category: Incident, Maintenance, Security Advisory, or Service Change. Anything else fails the build.
  4. Dates from git. Unless the front matter overrides them, a notice's published and updated dates are its first and latest commit in the repository's history. Dates never need maintaining by hand. CI checks out the full history so this works there too.
  5. Parse once, use three ways. The Markdown is parsed into a syntax tree a single time. That tree is walked to build the table of contents (second- and third-level headings, shown only when there are at least three), walked again to extract plain text for search (including code blocks, so searching for a command finds the notice that uses it), and finally rendered to HTML. Raw HTML in a notice is escaped, not rendered.
  6. Relationships. Once every notice is loaded, each one is linked to up to three others that share the most categories, and the notices are grouped into one page per category.

The engine also produces, for every notice:

  • A search index, embedded in the Notices page as JSON, which the browser searches as you type.
  • Structured data (schema.org Article) so search engines understand the title, description, dates and publisher.
  • An RSS feed entry, so readers can subscribe to new notices.

During build, notices are loaded once and cached, because the embedded files cannot change while the program runs. During serve, they are re-read on every request so edits appear immediately.

What runs in the browser

Upstream status

The status section fetches each provider's public status feed directly from the visitor's browser, which those feeds explicitly allow. Two kinds of status feed are supported, each with its own small adapter. The 90 daily bars are rebuilt from the incidents each provider has reported, so they show what was disclosed rather than measured uptime, and the page says so. If a feed is slow, blocked or changes format, that row shows a neutral state instead of an error, and the rest of the page is unaffected.

Notices

A second script adds copy buttons to code blocks, link icons to section headings, and live search and category filtering on the Notices page. All of it is progressive enhancement: without JavaScript, notices still read normally and the category filters are ordinary links to static category pages.

Validation and safety

The build stops, with a message naming the problem, if any of these are true:

  • A page refers to a template that does not exist, or a listed document is missing.
  • The custom domain file is missing, which would silently detach the site from its address.
  • The site address is not HTTPS.
  • A roadmap item has an unknown stage, or an FAQ entry is missing its question or answer.
  • A notice has no category, an unapproved category, unknown front matter, or a malformed date.
  • A notice contains anything that looks like a credential.
  • A status provider has a non-HTTPS endpoint, an endpoint that does not match its feed type, a missing label, or a label used twice.
  • A file named like a document that must never be published from this repository reappears.

Testing and CI

Unit tests cover the logic most likely to break quietly:

TestWhat it proves
Secret patternsEach pattern catches a realistic example, and ordinary technical prose does not trigger any of them.
Front matterValid blocks parse correctly; typos, bad dates, unclosed blocks, invalid categories and repeated keys are all rejected.
Table of contentsHeadings become correct entries and anchors, and short notices get no contents box.
Related noticesNotices sharing more categories rank first, and unrelated notices are never linked.
Titles and summariesThe title and first-paragraph summary are extracted, with Markdown formatting removed.
Feed, URLs and changelogThe RSS feed is well formed and escaped, canonical URLs are correct, and What's New reads the latest release.
Real contentThe site's actual content passes every validation rule.

On every push to the main branch, CI checks out the full history, runs go vet (static analysis), runs the tests, builds the site, and only then publishes. A failure at any step leaves the live site unchanged.

Trade-offs and limits

  • No server means nothing can be private. Every file published is public. Anything that must be restricted to certain people does not belong here.
  • Status reflects disclosure. The daily bars are only as complete as each provider's own incident reports.
  • Search is simple by design. It matches words in the browser, which is fast and needs no service, and suits a site with dozens of notices rather than thousands.
  • The development server reads the page list at start-up. Editing a notice shows on refresh, but adding a new one needs a restart.
