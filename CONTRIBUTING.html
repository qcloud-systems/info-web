Contributing Guidelines

QCS Trust & Status Center

Thank you for your interest in contributing to the QCS Trust & Status Center. To maintain consistency and quality, please follow the guidelines below.

Branching Strategy

  • main — Production. Changes reach it only through pull requests.
  • feature/<name> — New sections, notices, or layout enhancements.
  • fix/<name> — Bug fixes, typos, or minor improvements.

Commit Message Format

Use clear, descriptive commit messages:

  • docs: add new architecture diagram
  • style: improve sidebar spacing
  • fix: correct DNS instructions
  • feat: add dark mode toggle

Content Standards

  • Keep content concise, technical, and accurate.
  • Use consistent heading levels (h1, h2, h3).
  • Prefer lists and code blocks for clarity.
  • Avoid unnecessary dependencies — keep the site static and lightweight.
  • Everything here is public: never include credentials, client documents, or internal details.
  • If a change alters how the site is built, update the How It's Built page in the same pull request.

Writing a Notice

Notices are incident reports, maintenance windows, security advisories and service changes, published on the Notices page.

Review checklist

  • Accuracy. Dates, times and the affected services are correct, and the timeline matches what actually happened.
  • Safety. No hostnames, IP addresses, account IDs, internal tool names or other internal details, and nothing that would help an attacker. The build blocks common secret formats, but it cannot catch everything.
  • Category. One of the approved categories: Incident, Maintenance, Security Advisory or Service Change.
  • Clarity. A one-sentence description, and a title that says what happened, not just "Update".

Writing style

  • Lead with what happened and who was affected, then explain.
  • Give times with a time zone, for example "14:05–14:40 UTC".
  • Use plain language a non-engineer can follow.
  • One notice per event. When the situation changes, update the existing notice rather than posting a new one.
  • Say what is being done to prevent it happening again, once that is known.

Pull Request Process

  1. Fork the repository.
  2. Create a feature or fix branch.
  3. Commit changes with clear messages.
  4. Submit a pull request describing:
    • What changed
    • Why it changed
    • Any relevant context or screenshots

Code Style

  • Use semantic HTML.
  • Keep CSS modular and readable.
  • Avoid inline styles unless necessary.
  • Maintain accessibility (contrast, readable font sizes, ARIA labels when needed).
